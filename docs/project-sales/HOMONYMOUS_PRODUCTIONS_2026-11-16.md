# Одноимённые постановки: «В джазе только девушки»

Проверено **16.11.2026**, итерация 018. Только анализ сохранённых рабочих данных;
исключения, сборы, синхронизации и изменение приложения не запускались.

## Запрос и целевая постановка

Пользователь спросил, как отличить местные спектакли от нужной гастрольной версии
и можно ли проверить вручную и удалить неизвестные. По уточнению пользователя
целевая постановка связана с **Натальей Громушкиной**. Это ориентир для проверки,
а не подтверждённое соответствие конкретной строки каталога или команда удаления.

## Наблюдения

- В рабочем market/events.json — 28 будущих строк с точным названием
  «В джазе только девушки» в 19 городах. В API — 18 групп с этим точным названием:
  17 местных по подсказке классификатора и одна гастрольная из двух городов.
- Среди строк Кирова — 5 дат драматического театра, Кемерова — 5 дат музыкального
  театра Кузбасса, Волгограда — 2 даты муниципального музыкального театра.
  Отдельная версия «Девушки из джаза» сюда не включена.
- У 14 строк в разных городах общий ID мероприятия Яндекс Афиши
  `6582c66061be7b008732b648`, URL заканчивается на `v-dzhaze-tolko-devushki-gromko`.
  У Кирова, Кемерова и Волгограда другие ID источника. Это полезные признаки
  разных версий; связь первой цепочки именно с Натальей Громушкиной пока
  не подтверждена сохранёнными описаниями/афишами.
- Подсказка «репертуар: 4+ даты в одном городе» в curation._auto применяется
  ко всему одноимённому набору, если хотя бы в одном городе набрано четыре даты.
  Из-за этого показы разных версий получают одинаковую местную классификацию.
  Два вручную отмеченных прокатных зала остаются гастрольными.
- Организаторы отличаются даже в цепочке одного ID источника. Это могут быть
  региональные организаторы/продавцы; поле org не подтверждает продюсера постановки.
  В текущих сохранённых строках имя Натальи Громушкиной не найдено.

## Подтверждённая ошибка охвата удаления

Read-only SELECT рабочей PostgreSQL показал, что местные и гастрольные версии
с точным названием связаны с одним projects.id **1873**, scope пустой.
В review.catalogue местная подсказка разделяет их на строки по городу/площадке,
но это не создаёт независимые идентификаторы постановок в БД.

review.matches при равных ненулевых pid возвращает True **до проверки context**.
Защита protected_keys также не разделяет группы с одинаковым pid.
Поэтому визуально отдельная строка не гарантирует отдельное удаление истории.

Проверка выполнена чистым вызовом matches на копиях сохранённых строк с реальными
pid из read-only SELECT: правило пяти дат Кирова совпало с **28 из 28** строк,
включая все 14 строк общей гастрольной цепочки источника. apply/save/purge не вызывались.
Это проверка предиката, а не фактическое удаление и не замер времени очистки.

## Практический порядок и следующий шаг

Сейчас проверять вручную по билетной ссылке, афише, составу и продюсеру полезно.
Удаление неизвестного только по названию или подсказке local для этого случая
небезопасно. Неизвестная версия не означает местную постановку.

Перед выборочным удалением требуется исправить учёт context при общем pid,
проверить разделение на уровне БД и источников и регрессией доказать, что удаление
местной версии сохраняет гастрольные показы и их историю. Связь с продюсером
следует подтверждать афишей/составом; единый ID источника — дополнительный признак.
Подтверждённую версию можно затем отметить для сохранения, а сомнительные
проверять отдельно. Кнопка «Оставить» сейчас сама по себе не защищает от
ошибочно широкого правила исключения соседней группы.

Изменение правил, схемы группировки и интерфейса этой итерацией не внедрялось.
Реальные постановки агент не оставлял и не удалял. Следующий шаг — исправление
охвата и проверка целевой версии перед ручным удалением одноимённых постановок.
