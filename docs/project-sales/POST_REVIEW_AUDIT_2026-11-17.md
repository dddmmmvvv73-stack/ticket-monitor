## Проблема 1: удалены ранее оставленные группы

В 16:24 видимых kept было 101. После операции 16:28:21 (2 400 правил) стало 77.
В последнем пакете есть глобальные правила project с context={} для:

- «В джазе только девушки», pid=1873: в файле keep 17 групп этого названия;
- «Девчата», pid=720: в файле keep 7 групп этого названия.

Эти 24 ранее видимые группы теперь отсутствуют. Для точного названия
«В джазе только девушки» в sessions осталось 0 сеансов. Это относится к ранее
обсуждённой целевой постановке пользователя, поэтому нельзя объявлять процесс
полностью корректным или рекомендовать продолжить массовое удаление без исправления.
Отметка keep не защищает от широкого правила другой группы общего проекта.
Файл keep не пересекается с исключёнными group ID напрямую; конфликт косвенный.
Это проявление ранее найденной проблемы разделения версий и приоритета решений.

## Проблема 2: done при неполной очистке БД

При стабильной rev=164 обнаружены:

- 75 сеансов, совпадающих с текущими запретами: 66 с прошедшей датой, 9 с датой
  сегодня или позже; среди последних нет track_sales=true и status=on_sale;
- 87 listings, 48 pools, 403 observations по запрещённым ключам;
- последнее ts этих observations — 13.11, checked_at — 14.11. Это остатки,
  а не подтверждённый повторный сбор после сегодняшних исключений.

Примеры: «Шоу под дождём IV. Мужчина vs Женщина», «Оркестр в сиянии свечей
„Атмосфера“», «Музыкальное лото», «Невеста напрокат», варианты названия Богдана
Лисевского. В ряде случаев совпадение идёт по ключам при разных pid.

Механизм воспроизведён без рабочей БД: временные JSON + имитация PostgreSQL
в памяти, настоящий finalize_due/purge/enforce_db. В начале другой pid не
совпадает с правилом. Позже обработка файлов без pid удаляет строку по алиасу
названия и добавляет её ключ в правило. БД уже обработана и повторно не проверяется.
Результат: статус done, афиша пуста, в имитируемой БД остаётся сеанс, который
уже блокируется итоговым правилом. Это подтверждает ошибку порядка очистки.
Окончательное исправление должно также учитывать слишком широкие алиасы,
разделение разных постановок и защиту keep, а не просто удалять все остатки.
