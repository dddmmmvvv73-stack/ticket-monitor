## 1. Коротко

Инструмент анализирует конкурентов на рынке мероприятий: собирает афиши
площадок, классифицирует события по нишам (сфера / формат / жанр), считает
по схемам залов заполняемость, вал и выручку и копит историю.

Сейчас есть две части:

| Часть | Где | Статус |
|---|---|---|
| **Рабочее приложение** (Flask) | `app.py`, `competitors/`, `static/` | Работает: сбор, классификация, вал и выручка, аналитика. Интерфейс старый |
| **Прототип нового интерфейса** | `Design/prototype/index.html` | Утверждён пользователем. Работает на снимке данных, к серверу не подключён |

**Главная следующая задача** — перенести новый интерфейс из прототипа в
приложение (этап 1 плана ниже).

## 2. Как устроено приложение

Запуск: `python3 app.py` → `http://127.0.0.1:5050`. Пользователь держит
приложение запущенным у себя; после изменений кода его нужно перезапустить.

```
app.py                       Flask: страницы и API (/api/competitors/*, /api/analytics)
competitors/
  fetch.py                   загрузка HTML на urllib (без браузера), паузы между запросами
  dates.py                   разбор дат «18 ОКТЯБРЯ» без года
  odk33.py                   афиша ОДКиИ (odk33.ru) + схемы залов с vladimirkoncert.ru
  vladimirkoncert.py         билетный сайт: площадки, шоу, сеансы, схема зала
  seatmap.py                 разбор схемы по местам, цены мест, вал/выручка, бронь
  classifier.py              сфера/формат/жанр: ручные правки → правила → нейросеть
  gigachat_ai.py             GigaChat: сертификат Минцифры, клиент, построчный формат ответа
  collector.py               сбор целиком, склейка дублей, история, бронь, расписание, экспорт
static/
  index.html                 старый мониторинг Яндекс Афиши
  competitors.html           таблица конкурентов, настройки, бронь залов (старый вид)
  analytics.html             «Аналитика рынка» (старый вид)
config/                      источники, настройки, ручные правки, бронь залов, сертификат
data/competitors/            events.json, history/, seats/ (схемы залов), ai_cache.json, лог
Design/Reference/            референс стиля (Seline Analytics)
Design/prototype/index.html  утверждённый прототип нового интерфейса
.tastemaker/decisions.log    журнал дизайн-решений
```

Старая часть (мониторинг Яндекс Афиши через Playwright): `main.py`,
`scraper.py`, `processor.py`, `geometry.py`, `gross_potential.py`,
`alerts.py`, `sheets_export.py`.

### Ключевые решения по данным

- **«Занято» ≠ «продано».** На схеме зала видны места, которые нельзя
  купить: проданные, пригласительные и квоты других касс. Поэтому выручка —
  оценка сверху. Точная цифра — «подтверждённые продажи»: место было
  свободно в прошлом сборе и стало занятым. Они копятся только с начала
  слежения (с 29.09.2026); чем чаще сборы, тем точнее.
- **Цена занятого места** берётся по ряду: ряд определяется по координате Y
  на схеме, в одном ряду одна цена. Уровни точности: exact → row →
  neighbor → zone.
- **Место в зале опознаётся по ключу «зона | ряд | место»,** а не по
  пикселям: координаты «плавают» на 1px и сдвигаются из-за танцпола.
- **Бронь площадки** исключается из вала. Она определяется на двух уровнях:
  - места, занятые во всех событиях **зала** (от 3 событий);
  - места, занятые во всех событиях **одной рассадки**, то есть квоты серий.
    Пример: у пяти антреприз в «Арт Холле» закрыт один и тот же блок из
    439–451 места.

  Плюс ручные ряды. Зал — это группа рассадок площадки, совпадающих на ≥80%.
- **Классификация идёт в порядке приоритета:** ручная правка → правила по
  названию → тип на сайте → нейросеть. Ответы нейросети кэшируются.
- **GigaChat:**
  - бета-режим «ответ по JSON-схеме» ломается на пачках из 20+ элементов,
    поэтому используется построчный формат `номер | сфера | формат | жанр`;
  - на Python 3.9 клиенту нужен event loop, иначе он не работает в фоновых
    потоках (обход в `gigachat_ai._client`);
  - сертификат Минцифры скачивается сам, отпечаток закреплён в коде.

## 4. Прототип нового интерфейса — что утверждено

Файл `Design/prototype/index.html`, открывается двойным кликом. Данные — снимок
29.09.2026 по Владимиру (100 мероприятий), вшиты в файл.

**Каркас:**
- боковое меню: Обзор · Ниши · Мероприятия · (скоро: Динамика продаж,
  Площадки и залы, Архив, Настройки);
- шапка: город, период 30 / 90 дней / сезон, **календарь** (месяц или любой
  диапазон, дни в любом порядке, точки — дни с мероприятиями), поиск,
  «Собрать сейчас»;
- на телефоне нижняя панель вместо меню, таблица превращается в карточки.

**Мероприятия (главный раздел):**
- **7 колонок:** Дата (день недели; выходные красным) · Площадка / город ·
  Мероприятие (метки «под риском», «Пушкинская карта», «изменено
  вручную», «своё событие») · Ниша (сфера + жанр) · Заполняемость ·
  Цены · Вал · Выручка;
- **колонка «Заполняемость»:** полоса + %, под ней «занято X из Y ·
  осталось Z», ширина полосы равна ширине подписи;
- **цвет полосы:** красный — под риском (до события ≤ 21 дня и заполнено
  < 40%); зелёный — заполнено ≥ 60%; синий — продажи идут;
- **выручка без процента от вала:** пользователь попросил убрать, потому
  что проценты путали;
- **таблица:** сортировка по дате, заполняемости, цене, валу, выручке;
  подсказки «?» у заголовков;
- **фильтры:** подборки «Все / Под риском / Новые за 7 дней / Без жанра»;
  фильтр площадки и сферы;
- **настройка столбцов:** «Столбцы» — скрыть/показать (Дату и Название
  скрыть нельзя); ширина меняется перетаскиванием линии в заголовке,
  двойной клик сбрасывает; хранится в браузере;
- **компактность:** таблица не растягивается на широком экране;
- **кнопка «Добавить событие»:** своё мероприятие появляется во всех
  разделах.

**Карточка мероприятия** (выезжает справа поверх таблицы, ширина около 42%
экрана, от 480 до 880px):
- заголовок, метки ниши и статуса, **карандаш** (правка всех значений) и
  крестик;
- блоки 3 × 2: **Заполняемость** (цвет как в таблице) · **Занято /
  осталось** · **Выручка** / **Вал** · **Средний билет** · **Цены**;
- слева **Динамика продаж**: заглушка до накопления данных плюс блок
  **«Нужный темп до аншлага»**:
  - график от сегодняшнего числа занятых мест до полного зала;
  - внизу шкала дат: чаще к событию, реже вдали, с подписью месяца;
  - цифры: осталось, дней, в день, в неделю (если до события < 7 дней —
    «за N дн.»), выручка в день;
- справа **Зал по рядам**: полоса на ряд, длина = число мест. В прототипе
  есть только у «Кармен»;
- внизу во всю ширину **«Приезжал раньше»** (пока заглушка);
- ссылка **на конкретное мероприятие**:
  `vladimirkoncert.ru/shows/event/<id>`, для событий без продажи — страница
  odk33.ru;
- **форма правки:** проверки (обязательные поля, «занято ≤ мест», «от ≤
  до»); вал и выручка досчитываются по средней цене, если их не вписали;
  «Вернуть данные парсера»; удаление своего события.

**Обзор и Ниши:** как в первом прототипе. Обзор — главные цифры, что
изменилось, под риском, площадки, ближайшие 7 дней. Ниши — тепловая карта
«категория × площадка» с разрезами и мерами, плотность по месяцам, три
вывода.

**Стиль:**
- тёплый холст `#fafaf9`, белые карточки с рамкой `#e8e6e5`;
- один акцент: `#3ba6f1` (заливка, тёмный текст на ней) и `#1d6fae`
  (данные и ссылки);
- активное состояние `#1c1917`;
- статусы: красный `#d03b3b`, зелёный `#15803d`, выходные `#b91c1c`;
- шрифты Onest (заголовки) и Golos Text (интерфейс);
- анимации 120–300 мс, ease-out, выключаются при «уменьшить движение».

Все текстовые пары проверены: `tastemaker/scripts/check_contrast.py`,
`dataviz/scripts/validate_palette.js`, `audit_motion.py`.

## 5. План разработки по этапам

Порядок выбран так, чтобы каждый этап давал пользу сам по себе.

### Этап 0. Подготовка — почти готово
- ✅ git: репозиторий создан (ветка `main`). Секреты
  (`config/settings.json`) и данные (`data/`) исключены через
  `.gitignore`.
- ✅ Ротация `data/raw`: снимки старше 14 дней сжимаются в gzip

- ✅ Сбор включён: обе площадки, автосбор раз в час (с 29.09, 22:43).
  Работает, пока запущен `app.py`.
- ⬜ Закрепить версии зависимостей в `requirements*.txt`.

### Этап 1. Новый интерфейс в приложении ← главный
- Перенести прототип в `static/` (или новый шаблон) и подключить к
  реальному API вместо вшитого снимка: `/api/competitors/events`,
  `/api/analytics`, настройки, бронь.
- Хранить **ручные правки и свои события на сервере**, отдельно от данных
  парсера, чтобы новые сборы их не перезаписывали. Использовать тот же
  подход, что `config/classification_overrides.json`. Правки должны
  попадать в аналитику и экспорт.
- Хранить настройки таблицы на сервере или оставить в браузере — решить с
  пользователем.
- «Зал по рядам» для каждого события: данные уже есть в
  `data/competitors/seats/*.json`.
- Перенести в «Настройки»: источники, сбор и журнал, нейросеть, Google
  Таблицу. Бронь залов — в «Площадки и залы» (этап 5).
- Старые `competitors.html` и `analytics.html` убрать после переноса.

### Этап 2. Другие города
Все четыре сайта на том же движке, что vladimirkoncert. Нужно вынести
`BASE_URL` и город в параметры источника.

| Город | Источник | Площадки |
|---|---|---|
| Иваново | ivanovokoncert.ru | 13 |
| Кинешма | ivanovokoncert.ru | Кинешемский драмтеатр |
| Кострома | kostromakoncert.ru | 3 |
| Ярославль | yarkoncert.ru | 17 |
| Рыбинск | yarkoncert.ru | **уточнить**: предположительно ДК «Авиатор», «Вымпел» |
| Ковров | kovrovkoncert.ru | 4 |

- На yarkoncert фильтр `/shows?venue=ID`, похоже, работает иначе:
  у всех площадок первым отдаётся одно и то же шоу. Разобраться, как
  получить список площадки.
- Город брать из адреса площадки на странице сеанса. Сейчас город берётся
  из настроек источника.
- Нагрузка: сбор по 7 городам — сотни страниц. Нужны паузы и, возможно,
  разные интервалы для разных городов.

### Этап 3. Динамика продаж
- Фактический график в карточке по `history/` и подтверждённым
  продажам. Рядом — «нужный темп», чтобы было видно, успевает ли
  мероприятие.
- Раздел «Динамика продаж»: продажи рынка по дням, темп по площадкам,
  **кривые «продано за N дней до события»** для сравнения похожих
  мероприятий.
- Уведомления (Telegram или почта): всплески продаж, скидки, новые
  события, «под риском». Заготовка — `alerts.py`.

### Этап 4. Архив за год
- Фиксировать **итог на дату события** (последний снимок до начала) и не
  удалять прошедшие события.
- Экран «Архив»: поиск, фильтры по нише, городу, площадке.
- **Связывать повторные приезды** одного артиста или спектакля:
  нормализация названий, возможно с помощью нейросети. Блок «Приезжал
  раньше» в карточке — отсюда.

### Этап 5. Площадки и залы
- Страница площадок по городам: число событий, средняя заполняемость,
  выручка, средний чек.
- Залы: схема, бронь (авто и ручная, перенос из текущей панели «Бронь
  залов»), история заполняемости по зонам.

### Этап 6. Ниши глубже
- Разрез «ниша × город» (после этапа 2) и сравнение городов.
- «Свободные ниши» с учётом спроса: мало предложения при высокой
  заполняемости.
