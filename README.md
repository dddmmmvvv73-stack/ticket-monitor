# Мониторинг продаж билетов — как запустить

> Зачем этот инструмент и что он должен уметь — см. [GOALS.md](GOALS.md).
> Текущее состояние, решения и план разработки — [HANDOFF.md](HANDOFF.md).

## 0. Где сейчас идёт сбор

**С 05.10.2026 все сборы идут на сервере в Яндекс Облаке** (раньше — GitHub Actions + cron-job.org, теперь
отключены; ветка `data` на GitHub заморожена на 05.10). Расписание — systemd на сервере: площадки прямого сбора
(`tm-collect`) — каждый час в :25, афиша рынка (`tm-market`) — в 21:00, продажи гастролей (`tm-sales`) — каждый час
в :05, пересборка базы (`tm-sync`) — в :58, копия базы (`tm-backup`) — в 03:30. Данные — на сервере, история —
локальный git в `/opt/ticket-monitor/data/competitors`; на ноутбук — по SSH (адрес — `config/server.json`, не в git).
Подробности — [HANDOFF.md](HANDOFF.md), раздел 0, «Яндекс Облако».

**Интерфейс в браузере с любого компьютера (с 05.10):** сервер сам показывает прототип — `https://<IP через дефисы>.sslip.io`
(бесплатный адрес без покупки домена; точный адрес, логин и пароль — у владельца, в git их нет). Служба `tm-web`
за Caddy (https, вход по паролю — `/etc/caddy/Caddyfile`, образец — `deploy/Caddyfile.example`). Правки на сайте
сохраняются на сервере и сами уходят на GitHub; кнопка «Собрать сейчас» запускает сбор на сервере.

```bash
./pull_data.sh                  # данные и сводку продаж — с сервера в data/competitors
python3 app.py                  # открыть интерфейс, как раньше
ssh -i ~/.ssh/ticket_monitor_yc tm@<сервер> 'sudo systemctl start tm-collect'   # собрать сейчас (или кнопкой в «Настройках»)
ssh -i ~/.ssh/ticket_monitor_yc tm@<сервер> 'journalctl -u tm-collect -n 30'   # журнал сбора
```

**Афиша рынка** (98 городов по Кассиру и Яндекс Афише, раз в сутки в 21:00 МСК, на сервере) —
`competitors/market.py`, данные — `data/competitors/market`:

```bash
ssh … 'sudo systemctl start tm-market'          # собрать рынок на сервере прямо сейчас (~50 мин)
./pull_data.sh && python3 -m competitors.market export   # свежий снимок → раздел «Рынок» прототипа
MARKET_ONLY="Владимир,Иваново" python3 -m competitors.market   # проверочный сбор по паре городов (пишет в data/!)
```

Города списка — `config/market.json`, справочник регионов Кассира —
`config/market_kassir_regions.json`.

**Прототип нового интерфейса с сохранением разметки** — через приложение:
`python3 app.py` → http://127.0.0.1:5050/proto/ (разметка «гастроль / местное», типы
площадок, правки и фильтры пишутся в `config/market_curation.json` и сами уходят на GitHub;
данные рынка берутся из `data/competitors/market`, после `./pull_data.sh` — просто обновить страницу).
Мероприятия, залы и продажи конкурентов прототип берёт так же — из `data/competitors`
(`/proto/competitors-data.js`). Для прототипа, открытого файлом, снимок пересобирается командой
`./pull_data.sh && python3 -m competitors.protodata export`.
Избранные проекты и ваши записи о них («Репертуар → Избранное», «Мои записи») хранятся только на этом
компьютере — `config/my_projects.json`, файл исключён из git и на GitHub не уходит.
Через приложение в прототипе всё рабочее: правки и свои мероприятия, бронь залов, площадки и настройки
сохраняются (и уходят на GitHub, кроме ключей), «Собрать сейчас» запускает сбор на GitHub, а
«Настройки → Сбор и журнал → Обновить данные с GitHub» выполняет `./pull_data.sh` и перезагружает страницу.

Площадки подключаются на странице «Конкуренты» (`/competitors`): билетный
сайт → площадка → город. Список сохраняется в `config/competitors.json` и
сам уходит на GitHub, сбор подхватывает его со следующего запуска.

**База данных** (шаг 4 плана, [DATA_MODEL.md](DATA_MODEL.md)) — пока параллельно файлам: сбор и прототип
её не читают. На ноутбуке — локальный Postgres 16 (пакет `pgserver`, файлы в `data/pgdata`, не в git):

```bash
python3 -m pip install --user -r requirements-db.txt   # один раз
python3 -m db.sync             # пополнить базу из data/competitors и config/ (с 05.10 база главная — ничего не стирается)
python3 -m db.sync verify      # только сверка с файлами
python3 -m sales.results       # итоги начавшихся и снятых сеансов (на сервере — каждый час, tm-sync)
python3 -m sales.history 2026-10-01 2026-10-31 Рязань   # архив за период (JSON) — то, что показывает «Архив»
python3 -m db.migrate stop     # остановить локальный Postgres
```

## Способ А — простой веб-интерфейс (рекомендуется)

```bash
python3 app.py
```

Автоматически откроется страница в браузере на `http://127.0.0.1:5050`.
Там можно:
- вставлять ссылки на события и нажимать «Начать парсинг»,
- смотреть красивые карточки с продажами и цветными статусами,
- настраивать административные (закрытые для продажи) ряды для каждой площадки,
- скачивать текущие результаты в CSV.

Чтобы остановить — вернись в терминал и нажми `Ctrl+C`.

### Вкладка «Конкуренты»

`http://127.0.0.1:5050/competitors` — таблица афиш площадок-конкурентов:
название, дата/время, зал, **сфера / формат / жанр**, цена от–до,
заполняемость зала, «Пушкинская карта».

- **Площадки.** По умолчанию — ОДКиИ Владимир (odk33.ru). Там же можно
  добавить любую из ~20 площадок, которые продают билеты через
  vladimirkoncert.ru (филармония, драмтеатр, «Полярис»…).
- **Сбор.** Кнопка «Собрать сейчас» или тумблер «Автосбор» с интервалом
  в минутах / часах / днях. Автосбор работает, пока запущен `app.py`.
  Прогресс и ошибки видны в «Журнале» — терминал смотреть не нужно.
- **Цены и заполняемость.** Если мероприятие продаётся через
  vladimirkoncert.ru, цены берутся из схемы зала (все ценовые категории),
  а заполняемость = занятые места / все места. Занятые включают места,
  которые площадка не продаёт онлайн (бронь), поэтому даже у свежего
  события заполняемость не нулевая. История изменений — в
  `data/competitors/history/`.
- **Сфера / формат / жанр** определяются в три слоя:
  1. ключевые слова в названии и тип мероприятия на билетном сайте;
  2. то, что осталось пустым, доопределяет нейросеть; ответы кэшируются.
     По умолчанию — **GigaChat** (Сбер, бесплатно для физлиц, без VPN).
     Нужен пакет (`python3 -m pip install -r requirements-ai.txt`) и ключ
     авторизации с developers.sber.ru — вставляется в «Настройках», там же
     пошаговая инструкция и кнопка «Проверить подключение». Сертификат
     Минцифры, который требует GigaChat, программа скачивает сама
     (с проверкой отпечатка) в `config/certs/`. Альтернатива — Claude (платно);
  3. ручная правка — клик по ячейке в таблице. Правка применяется ко всем
     датам мероприятия с таким названием и имеет высший приоритет.
- **Выгрузка**: CSV или Google Таблица.
- **Вал и выручка** (для мероприятий со схемой зала на vladimirkoncert.ru):
  - *вал* — все продаваемые места × цена;
  - *выручка (оценка)* — занятые места × цена; оценка сверху, т.к. «занято»
    включает пригласительные и квоты других касс;
  - *подтверждённые продажи* — место было свободно в прошлом сборе и стало
    занятым; точно, но только с начала слежения (чаще сборы — точнее динамика).
  Цена занятого места восстанавливается по ряду (ряд определяется по
  координатам на схеме). Бронь площадки не входит в вал: авто — места,
  занятые во всех мероприятиях зала (от 3 мероприятий), и ручная — ряды,
  отмеченные в панели «Бронь залов». Подробности — в `competitors/seatmap.py`.

### Вкладка «Аналитика рынка»

`http://127.0.0.1:5050/analytics` — рынок целиком: выручка и вал по площадкам
и сферам, нагрузка по неделям (где конкуренты сталкиваются датами),
подтверждённые продажи по дням, лидеры, быстрее всего продающиеся,
мероприятия под риском (скоро, а зал пуст) и новое в афишах.
Фильтры: период, площадка, сфера.

Разовый сбор без интерфейса: `python3 -m competitors.collector`.

#### Google Таблица для конкурентов

Выгрузка работает через веб-приложение Apps Script, поэтому пакеты
gspread/cryptography не нужны:

1. Google Таблица → «Расширения» → «Apps Script», вставить код из
   раздела «Настройки» на вкладке «Конкуренты» (там же пошаговая инструкция).
2. «Развернуть» → «Новое развертывание» → «Веб-приложение»,
   доступ «Все» → скопировать ссылку `…/exec`.
3. Вставить ссылку в настройках и нажать «В Google Таблицу»
   (или включить автовыгрузку после каждого сбора).

## 2. Настрой список событий

Открой `config/events.json` и добавь свои события — просто копируй блок
и меняй `id`, `url`, `venue`. `venue` — это ключ, по которому подтягивается
справочник заблокированных мест из `config/exclusions.json`.

## 3. Заполни справочник заблокированных мест

В `config/exclusions.json` для каждой площадки (`venue`) укажи:
- `reserved_seats_count` — сколько мест площадка держит для своих нужд
  (сотрудники и т.п.), если знаешь только число, не конкретные места.
- `excluded_seat_ids` — конкретные `sourceSeatId`, если знаешь их точно
  (увидишь такие id в сыром JSON в `data/raw/.../*.json`, поле `sourceSeatId`
  у каждого места).

## 4. Разовый тестовый запуск

```bash
python3 main.py
```

Должно вывести что-то вроде:
```
[korolshut-krasnoe-sormovo] Проверяю...
[korolshut-krasnoe-sormovo] Продано за проверку: 0 (+0 ₽). Свободно: 366/816. Статус: активно.
```

## 5. Автоматический запуск каждую минуту (macOS/Linux)

```bash
crontab -e
```
Добавь строку (поменяй путь на свой):
```
* * * * * cd /Users/имя/Desktop/Parser/ticket_monitor && /usr/bin/python3 main.py >> run.log 2>&1
```
Скрипт сам решает, какое событие пора проверять — лишних запросов даже
при вызове раз в минуту не будет (см. `MIN_SECONDS_BETWEEN_CHECKS` в main.py).

## 6. Google Таблица

Настройка — см. подробную инструкцию в шапке `sheets_export.py`.
После разовой настройки добавь в тот же crontab отдельной строкой,
реже — раз в 10 минут:

## Что где лежит после запуска

```
data/
  raw/{event_id}/2026-08-19_143000.json   ← сырые снимки, для пересчёта задним числом
  processed/{event_id}.json                ← готовые метрики по дням, отсюда берёт sheets_export.py
  state/{event_id}.json                    ← служебное состояние (какие места видели свободными в прошлый раз)
```

## Метрики, которые считаются в каждой записи `processed/{event_id}.json`

- `sellable_total` / `sellable_available` / `sellable_sold_cumulative` — с поправкой на резерв площадки
- `sold_today_count` / `revenue_today` — продано и заработано именно за этот интервал
- `revenue_cumulative_tracked` — накопленная выручка с начала слежения (не с начала продаж!)
- `discounts_detected` — места, где текущая цена ниже первоначальной
- `price_map_by_row` — раскладка цен по рядам (диапазоны ценообразования)
- `sold_share_by_row` — доля распроданности каждого ряда с начала слежения (покупательский паттерн)
- `operators` — какие билетные операторы продают событие через этот виджет
